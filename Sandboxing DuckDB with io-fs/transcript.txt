DuckDB is an embedded SQL database optimized for analytics workloads. The way I
like to describe it is: it's SQLite, but for analytics. Where SQLite stores rows
and is optimized for transactional workloads, DuckDB is columnar, vectorized,
and optimized for scanning and aggregating large amounts of data. It runs in
your process, there's no server, no cluster, no operations. And it's a real
database: full SQL support, inserts, updates, transactions, the whole thing.

But here's the part that I find the most powerful, and it's not the database
part at all. DuckDB can query almost anything. You can point it at a CSV file
and select from it. You can point it at JSON. You can point it at Parquet files
and it will read the metadata, use the column statistics, and only fetch the
pages it needs. And that's just the built-in formats.

Then there's the extension ecosystem, and this is where it gets a little bit
crazy. There are extensions to query files over HTTP, on S3, on GCS. There are
extensions to connect to Postgres, to ClickHouse, to Iceberg tables.
And because it's all SQL, you can join across all of these in a single query.
You can join a Parquet file on S3 with a Postgres table and a CSV
file on your laptop, in one statement.

In the Go ecosystem, we have a strong tendency to rewrite everything in Go. And

But it hasn't moved infinitely. There are still pieces of software that cross
the threshold where reusing beats rewriting, and a query engine like DuckDB is
firmly on the other side of that line. There are decades of query optimization
research in there, thousands of contributors, an enormous test surface, and a
level of maturity you do not regenerate with a prompt. Not every great piece of
software can be written in Go, and that's fine. For DuckDB, embedding the C++
code through CGO is simply the right call.

Closing the parenthesis. Because even when CGO is the right call, you inherit a
very specific set of problems. And the root of all of them is this: you end up
with two I/O stacks in one binary.

On one side, the Go runtime manages I/O through the io and net packages. We get
goroutines, we get the scheduler multiplexing them across CPUs, we get the
netpoller. It's a beautiful, coherent world.

On the other side, DuckDB's I/O stack is a whole different beast. It has its own
thread pools, its own buffering, its own HTTP client, its own retry logic. And
now, to understand the behavior or the performance of your service, you need to
understand how those two worlds interact. Trust me, that is not a fun debugging
session.

Speaking of debugging: all the tools we love just stop working at the CGO
boundary. pprof cannot see into the C++ side of the program. Your OpenTelemetry
instrumentation doesn't exist over there. From the Go side, a query is one giant
opaque function call: it enters CGO, time passes, results come out. What did it
read? How many requests did it make to S3? Was the cache warm? You don't know.

And then there's authentication, which is where this gets genuinely painful. Our
Go application already uses the AWS SDK. Credentials are configured, they
rotate, role assumption works, all of it battle-tested. But DuckDB doesn't know
about any of that. To let it read from S3, you install another extension, and
you configure a whole different HTTP client, with its own credential chain, its
own set of subtle behavior differences, and its own bugs. We had this problem
solved once in our application, and now we have to solve it a second time, in a
different language, inside a library we don't control.

By embedding DuckDB, we inherited a whole bag of problems that Go normally
solves for us out of the box. And I want to emphasize: this is not specific to
us. Every Go application embedding DuckDB, and honestly, every Go application
embedding any C library that does its own I/O, runs into exactly this.


So how did we solve it?

Here's the thing: DuckDB is really well architected. All I/O in DuckDB, every
single file operation, goes through a virtual file system abstraction. There's a
FileSystem base class in the C++ code, and everything above it, the Parquet
reader, the CSV reader, the buffer manager, only talks to that interface. By
default, DuckDB is compiled with an implementation that uses the local file
system. Extensions like httpfs work by plugging alternative implementations into
that same abstraction.

And when I saw that, I thought to myself: wait. If httpfs can inject a file
system, can I write my own virtual file system, and use CGO to inject Go into
it?

Because Go also has an abstraction for virtual file systems. It's the io/fs
package, added in Go 1.16, and at its center is the fs.FS interface. And I love
this interface, it's one method: Open takes a name, returns a file. That's it.
The standard library gives you implementations for free: os.DirFS for a real
directory, embed.FS for files compiled into your binary, fstest.MapFS for
in-memory testing. And half the ecosystem already implements it.

Now, fs.FS is read-only. There's no Write in the interface. But remember, we use
DuckDB as a query engine only. We never write. Read-only is not a limitation for
us, it's actually exactly the contract we want.

So that's what we built, and it's open-source:
github.com/firetiger-oss/go-duckfs. The package lets you mount any fs.FS as the
virtual file system backing a DuckDB database.

Let me show you what using it looks like. You call duckfs.Open, and you hand it
a file system, say, os.DirFS of a data directory. You get back a connector, you
pass that to sql.OpenDB, and from here on, it's just database/sql, the standard
interfaces you already know. You run a query like SELECT star FROM read_parquet
of data.parquet, and when DuckDB opens that file, it's not touching the
operating system. It's calling your fs.FS.

And the paths are just strings, so they can be anything your file system
understands. You can register a file system that handles paths like
"s3://bucket/table/file.parquet", and DuckDB will happily pass the whole thing
to your Open method. We'll come back to why that's so powerful in a minute.

How does it work inside? Two pieces, and both are small.

The first piece is a C++ extension, about three hundred and fifty lines. It
subclasses DuckDB's FileSystem class with a class we call GoFileSystem, and
every method, open, read, seek, glob, stat, is a one-liner that forwards the
call to an exported Go function.

The second piece is the Go side, about six hundred lines. Each exported function
is a little trampoline. Let me walk you through just one so you get the flavor:
the read function. DuckDB calls duckfs_file_read_at with a file ID, a pointer to
a buffer, a size, and an offset. On the Go side, we look up the fs.File for that
ID in a registry, we check that it implements io.ReaderAt, we wrap the C buffer
in a byte slice with unsafe.Slice, no copy, we're reading straight into DuckDB's
own memory, and we call ReadAt. The number of bytes read goes back across the
boundary. That's the entire function. Every other operation looks just like it.

So the whole bridge, the thing this talk is about, is under a thousand lines of
code. The pattern is small. What it unlocks is not.


Because here's what we get out of this.

First, sandboxing, it's in the title of the talk. Every single I/O operation
DuckDB performs now goes through an interface we control. DuckDB cannot open a
socket, cannot read a file, cannot touch anything we didn't explicitly hand it.
If the file system we mount only exposes one customer's data, then that query,
no matter what SQL the agent generated, can only ever read that customer's data.
The sandbox isn't a policy we check, it's a structural property of the program.
And when your queries are written by AI agents, let me tell you, that property
helps you sleep at night.

Second, observability. Every byte DuckDB reads now flows through Go code, which
means we can instrument all of it with the same tools as the rest of the
application. And there's a nice technique here worth stealing: fs.FS doesn't
take a context, but Open is just a method on a value you construct. So for each
incoming RPC, we build a file system value that closes over the request's
context, and mount that. Now every file operation DuckDB performs is attached to
the OpenTelemetry trace of the request that triggered it. We get end-to-end
tracing: the incoming RPC, the query, every read against object storage, all in
one trace. When a query is slow, we see exactly why. Cache misses, poor
pushdown, an authentication error three layers down, it's all right there in the
trace, instead of being invisible inside a C++ black box.

Third, virtualization means we can plug in any backend. Remember, our data is in
Iceberg tables on S3 and GCS. When DuckDB asks for "s3://" something, our Open
method sees the prefix, picks the AWS client; "gs://", it picks the GCS client.
And these are the same client instances the rest of the application already
uses. Same credentials, same configuration, same connection pools, same retry
logic. That painful "configure authentication twice" problem? It's just gone.
There is nothing to configure on the DuckDB side, because DuckDB no longer does
I/O.

Fourth, performance. Because the file system is just a value, we can wrap it. We
inject a caching layer between DuckDB and object storage, page-cache style,
sized to our workload, shared across queries. That's a plain fs.FS wrapper,
ordinary Go code, unit-testable, instrumented like everything else.

Fifth, and this is the one I didn't anticipate loving so much: testing. The
standard library ships fstest.MapFS, an in-memory fs.FS built from a map. So in
our tests, we craft a map of files in Go, mount it, and run a full DuckDB query
engine against it. No fixtures on disk, no Docker, no network. You construct a
corrupted Parquet file in memory and verify the query fails the way it should.
Testing an embedded C++ database with a map literal. It's delightful.

And finally, security in a broader sense. Think about what's left running as C++
in this design: pure computation over in-memory data. Parsing, planning,
executing, that's it. All I/O, including TLS, certificate validation, credential
handling, happens in Go, in the same code paths as the rest of the application,
in a memory-safe language. The C++ attack surface shrinks down to, essentially,
pure functions.

One small package. All the CGO integration problems we listed, solved. Plus
capabilities we didn't have before.
